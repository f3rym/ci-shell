# Проект: вытягивание артефактов джобы (ART-01)

Этот документ спроектирован по `ART-01` (v0.3.2), но НЕ реализован: ни строки кода `internal/`/`cmd/` этой фазой не тронуто. Документ кодирует решения для будущей фазы реализации `NEXT-03` («восстановление артефактов предыдущих стадий»).

`Provider.Artifacts(ctx, job) ([]Artifact, error)` объявлен в интерфейсе с Фазы 1 (`internal/provider/provider.go`, строки 25-26). Реализация GitLab (`internal/provider/gitlab/gitlab.go:375-379`) сегодня безусловно возвращает `ErrNotSupported`, оборачивая `NEXT-03` в текст ошибки:

```go
// Artifacts — скачивание артефактов предыдущих стадий. Это требование
// NEXT-03 (этап 1 из idea, v2), в Фазе 1 не реализовано.
func (c *Client) Artifacts(ctx context.Context, job provider.Job) ([]provider.Artifact, error) {
	return nil, fmt.Errorf("gitlab: скачивание артефактов — см. NEXT-03: %w", provider.ErrNotSupported)
}
```

То есть метод объявлен в интерфейсе с первого дня, но ни разу не реализован ни для одного провайдера — не «почти готово», а честная заглушка.

## 0. Статус и рамки

Эта фаза — решения, а не код: следующая фаза реализации (NEXT-03, следующий майлстоун) читает этот документ и пишет код без повторного исследования кодовой базы. Ни один файл `internal/`/`cmd/` в рамках этой фазы не открывается на запись — гейты плана это проверяют.

## 1. Откуда берутся артефакты

**Решение:** метаданные (список файлов, размер, тип) и содержимое (сами байты) — РАЗНЫЕ вызовы API, а не один.

Метаданные приходят из уже существующего эндпоинта `GET /projects/:id/jobs/:job_id` (используется `JobByID`, `internal/provider/gitlab/gitlab.go:311-327`) — GitLab отдаёт там же поле `artifacts` (массив `{filename, size, file_type, file_format}`), которое сегодня в `jobResponse`/`toJob` (`internal/provider/gitlab/gitlab.go:283-308, 342-367`) не разбирается вовсе. `Provider.Artifacts(ctx, job)` реализуется отдельным вызовом того же `GET /projects/:id/jobs/:job_id` для конкретной джобы-источника, а НЕ прибавлением поля `Artifacts []Artifact` к общей структуре `provider.Job` (`internal/provider/provider.go:70-91`) — `Job` используется как лёгкая структура в десятке мест (списки, заголовки экранов, лог), и тащить через все них неиспользуемый почти везде массив значило бы раздувать самый частый тип проекта ради одного потребителя.

Содержимое (сам архив) — новый эндпоинт `GET /projects/:id/jobs/:job_id/artifacts`, отдающий zip целиком за одну джобу. Новый метод `ArtifactsArchive(ctx context.Context, projectPath string, jobID int64) (io.ReadCloser, int64, error)` в интерфейсе `Provider` (`int64` — `Content-Length`, `-1`, если сервер его не прислал — то же соглашение, что и у `http.Response.ContentLength`), реализуется поверх `c.request` НАПРЯМУЮ (как `JobLog`, `internal/provider/gitlab/log.go:36-93`, не через `do`/`doPaged`) — тело НЕ читается внутри метода, возвращается вызывающему открытым (та же форма, что уже описана в комментарии `request`, `internal/provider/gitlab/gitlab.go`, строки 88-93). Причина: размер архива непредсказуем, а буферизация в память (как в `do`, предел `maxResponseBytes` 10 МиБ, `internal/provider/gitlab/gitlab.go:23`) для сотен мегабайт не годится — стриминг с внешним пределом (раздел 4) обязателен.

**Отвергнутая альтернатива:** доставать содержимое по одному файлу через `GET /projects/:id/jobs/:job_id/artifacts/:artifact_path` — работает только для одного известного имени файла за раз, требует по запросу на файл вместо одного на джобу, и не решает вопрос «что делать, если в архиве файл, о котором метаданные ничего не сказали» (десинхронизация списка и содержимого архива).

**Решение:** (права токена) тот же `PRIVATE-TOKEN` (`c.token.Secret`, тот же заголовок, что и во всех остальных вызовах `Client`, `internal/provider/gitlab/gitlab.go:99`), область `read_api` — которой уже достаточно для всего остального обхода (README, раздел «Использование»: «нужны области read_api и read_repository»). Область токена ради артефактов не вводится, README не меняется.

Отказ по правам (401/403 на `/artifacts`) в GitLab означает НЕ обязательно отклонённый токен целиком, а может означать ограничение доступа к артефактам на уровне настроек проекта (Settings → CI/CD → Artifacts access). Решение — перехватывать `errors.Is(err, provider.ErrUnauthorized)` именно в новом методе/пакете артефактов и переоборачивать в СВОЙ текст («артефакты недоступны этому токену — проверьте ограничение доступа к артефактам в настройках проекта, а не обязательно сам токен»), не теряя `errors.Is`-совместимости с `ErrUnauthorized` (оборачивание через `%w`, тот же приём, что уже применён к каждой sentinel-ошибке `gitlab.go`).

**Отвергнутая альтернатива:** заводить отдельную sentinel-ошибку `ErrArtifactsForbidden` вместо переиспользования `ErrUnauthorized` — усложнило бы код вызывающей стороны (два разных `errors.Is` для похожих по сути отказов доступа) без выигрыша: сообщение уточняется текстом, не типом ошибки.

## 2. Артефакты каких джоб

**Решение:** нужны артефакты джоб, ОТ КОТОРЫХ упавшая джоба зависит (`dependencies:`/`needs:` из её конфига), а НЕ её собственные — упавшая джоба ничего не произвела (упала до `script`, либо её собственные артефакты нерелевантны воспроизведению входного состояния), а восстанавливать нужно именно то, что она ПОЛУЧИЛА от предыдущих стадий на входе. Это подтверждается дословно: `idea`, строка 126, «Артефакты предыдущих стадий — скачиваются через API и распаковываются в рабочий каталог». Решение подтверждает первоначальный комментарий `Provider.Artifacts` Фазы 1 («артефакты предыдущих стадий для джобы», `internal/provider/provider.go:25`) — уточняется здесь только механизм получения (раздел 1).

**Решение:** (правило отбора) по документированному поведению `dependencies:`/`needs:` в GitLab CI (точная формулировка сверяется с официальной документацией — задача фазы реализации; ниже решение фиксируется по памяти проекта и логике, а не как дословная цитата):

- (а) ключ `dependencies:` отсутствует в конфиге джобы вовсе → артефакты берутся от ВСЕХ джоб более ранних стадий;
- (б) `dependencies: []` (явно пустой список) → артефакты не берутся вовсе;
- (в) `dependencies: [job1, job2]` → только перечисленные;
- (г) `needs:` (короткая форма `needs: [job1, job2]` или отображение `needs: [{job: job1, artifacts: true}]`) → артефакты только от перечисленных, порядок стадий не имеет значения (DAG), `artifacts:` внутри `needs` по умолчанию `true`, когда джоба указана короткой формой.

`dependencies:`/`needs:` сегодня НИГДЕ не разбираются (`internal/provider/gitlab/config.go`, `buildJobConfig`, строки 130-175 — ни одного упоминания). Фаза реализации добавляет в `provider.JobConfig` два новых поля: `Dependencies []string` (`nil` — ключ отсутствует в конфиге; отличие `nil` от пустого `[]string{}` ОБЯЗАНО сохраниться — это и есть развилка (а)/(б) выше, схлопывать их в одно значение нельзя) и `Needs []NeedRef`, новый экспортируемый тип `NeedRef{Job string; Artifacts bool}`. Парсинг — новая функция `resolveDependencies`/`resolveNeeds` рядом с `buildJobConfig` в `internal/provider/gitlab/config.go`, тем же приёмом, что уже применён к `decodeScriptList`/`decodeEnvironment` в этом файле.

**Решение:** (разрешение имени в ID) переиспользовать уже существующий постраничный метод `PipelineJobs(ctx, projectPath, pipelineID, req)` (`internal/provider/provider.go`, строка 64; уже возвращает `Page[Job]`) с `pipelineID = job.PipelineID` упавшей джобы, пройти страницы, сопоставить по `Name`.

**Отвергнутая альтернатива:** заводить новый метод `JobByName` — `PipelineJobs` уже решает эту задачу постранично, второй метод с тем же результатом задублировал бы код без причины.

**Решение:** (явная граница) `needs:` с межпроектной/межпайплайновой формой (`needs: [{project: ..., job: ..., ref: ...}]`) и джобы `parallel:`/матрицы (несколько экземпляров джобы с одним базовым именем, суффиксы вида `job 1/3`) — вне этого решения; резолвер по имени внутри ОДНОГО пайплайна их не различает и не обязан на этом этапе (детализируется в разделе 7).

**Отвергнутая альтернатива:** сразу проектировать полную поддержку — расширило бы фазу за рамки «одна упавшая джоба, её прямые зависимости внутри того же пайплайна», которые единственно нужны для v0.1.0-класса сценариев проекта (простые пайплайны, как и остальные ограничения `Scope` в `PROJECT.md`).

## 3. Куда кладутся

**Решение:** (путь внутри контейнера) тот же `CI_PROJECT_DIR`, что и у кода (`env.Environment.WorkDir()`, `internal/env/env.go:154`; по умолчанию `/builds/<ProjectPath>`, `internal/env/predefined.go:60`) — так поступает и настоящий GitLab-ранер: артефакты распаковываются ПОВЕРХ рабочего каталога джобы, не в отдельный подкаталог.

**Решение:** (путь на хосте) ТОТ ЖЕ каталог, что и чекаут кода: `Checkout.Dir`, возвращённый `repo.Materialize` (`internal/repo/checkout.go`, структура `Checkout`, поле `Dir`, строки 52-67) — он и есть `spec.SourceDir`, монтируемый 1:1 в `spec.WorkDir` (`cmd/ci/main.go`, сборка `spec`, строки 404-412; `internal/ui/session.go`, строки 297-305). Артефакты распаковываются НАПРЯМУЮ в `Checkout.Dir`, никакого нового подкаталога `internal/cache` не заводится — `cache.Dir`/`cache.CheckoutBase` (`internal/cache/cache.go:113-196`) остаются единственным местом решения о расположении, эта фаза их не меняет и не добавляет новую категорию каталога.

**Отвергнутая альтернатива:** распаковывать в отдельный host-каталог и монтировать вторым `docker run -v` поверх образа — раздвоило бы источник правды о содержимом рабочего каталога джобы (`runner.Spec` сегодня несёт ровно один `SourceDir`/`WorkDir`), лишний код в `internal/runner/docker.go`, и разошлось бы с тем, как это делает настоящий GitLab-ранер (единый рабочий каталог).

**Решение:** (пакет-владелец) новый `internal/artifacts`, НЕ `internal/repo` — `repo` сегодня не импортирует `internal/provider` вовсе (git и файловая система, проверено — ни `Materialize`, ни `Prepare`, ни `mirror.go` не ссылаются на `provider.Provider`/`provider.Job`), а скачивание архива обязано идти через `Provider` (нужны `provider.Job`, `provider.JobConfig.Dependencies/Needs`, новый `ArtifactsArchive`). Смешение затащило бы HTTP-транспорт в пакет, объявляющий о себе «git и файловая система, больше ничего».

Форма — по образцу `internal/repo`: `Request` (упавшая джоба, её `JobConfig`, `Provider`, целевой каталог — тот же `Checkout.Dir`, `event.Emitter`) и единственная точка входа `Restore(ctx context.Context, req Request, em event.Emitter) (*Result, error)`, симметрично `repo.Materialize`.

**Решение:** (точка вызова, детализируется в разделе 6) сразу после `repo.Materialize` в обоих местах, где он сегодня вызывается — `cmd/ci/main.go`, функция `reproduce` (вызов `repo.Materialize`, строки 326-338), и `internal/ui/session.go`, `PrepareCmd` (вызов `repo.Materialize`, строки 267-279) — оба места сегодня почти дословно повторяют один и тот же порядок вызовов, что подтверждает симметрию точки внедрения.

## 4. Размер и прогресс

**Решение:** (клиентский предел размера) НЕЗАВИСИМО от серверных лимитов GitLab (они настраиваются администратором инстанса и меняются между версиями/тарифами, полагаться на конкретное число нельзя): новая именованная константа `provider.DefaultArtifactSizeLimit`, по аналогии с уже существующей `provider.DefaultTailBytes` (`internal/provider/provider.go:296`, 64 КиБ для хвоста лога) — предложенное значение 500 МиБ (`500 * 1024 * 1024`), с настройкой переопределения по тому же приёму, что `settings.CacheDir`/`settings.CheckoutDir` (`internal/cache/cache.go`, `computeBaseLocked`/`CheckoutBase` читают `config.Load()`).

**Решение:** (проверка предела) ДВЕ точки, не одна:

1. до начала чтения тела — если `Content-Length` известен (не `-1`) и превышает предел, отказ немедленно, без единого байта по сети;
2. во время самого чтения — `io.LimitReader(body, limit+1)` и проверка, что прочитано СТРОГО не больше `limit` (`Content-Length` может отсутствовать или врать) — при превышении отказ с сообщением, сколько байт уже пришло и какой предел, БЕЗ попытки использовать частично скачанный архив (усечённый zip — это просто битый архив, не частичный результат).

**Отвергнутая альтернатива:** молча брать первые N байт и пытаться распаковать то, что получилось — испорченный архив ронял бы `archive/zip.NewReader` с невнятной для человека ошибкой вместо честного «артефакты больше 500 МиБ, пропускаю».

**Решение:** (прогресс) переиспользуется словарь `internal/event` (закрытый список типов, `struct` + `isEvent()`, тот же приём, что у `CodePreparing`/`CodeReady`, `ImageLocal`/`ImagePulling`, `internal/event/event.go`), НЕ новая подсистема:

- `ArtifactsFetching{Total int}` — сколько джоб-источников артефактов резолвнуто;
- `ArtifactDownloading{Job string, Bytes int64}` — `Bytes` — `Content-Length`, 0, если неизвестен;
- `ArtifactsExtracted{Job string, Files int}` — по одной на каждую распакованную;
- `ArtifactsReady{Files int, Bytes int64}` — итог;
- `ArtifactsSkipped{Reason string}` — `dependencies: []`, либо зависимостей нет вовсе;
- `ArtifactsUnavailable{Job string, Reason string}` — 403/404 по одному источнику, не прерывает восстановление остальных (раздел 5).

Дискретные вехи, БЕЗ побайтового прогресс-бара — по прецеденту `ImagePulling`/`ImageLocal` (`internal/event/event.go:47-58`), которые тоже не несут процента закачки образа, при том что образы часто крупнее артефактов.

**Отвергнутая альтернатива:** побайтовый тикер прогресса (проценты, обновляемые по ходу чтения) — новая инфраструктура (таймер, троттлинг событий) ради операции, которая для типичных артефактов (десятки-сотни МиБ) занимает секунды; вводить стоит только если реальное использование покажет нужду — фаза реализации может добавить ПОЗЖЕ, не меняя структуру решения здесь.

## 5. Срок жизни

**Решение:** артефакты GitLab истекают по `expire_in` (настройка джобы в `.gitlab-ci.yml`); после истечения `GET .../artifacts` отвечает 404 — тем же кодом, каким GitLab отвечает и на «у джобы вообще никогда не было артефактов». GitLab НЕ различает эти два случая в самом статусе ответа, доп. вызовов ради различения не делать — единое сообщение-предупреждение по образцу `ErrLogUnavailable` (`internal/provider/provider.go:317`, «у джобы может не быть лога вовсе… это не поломка, а нормальная ветка») и `VariableSet.Notes` (`internal/provider/provider.go:164-167`, честные оговорки о недоступных источниках, не прерывающие обход остальных).

Новая sentinel-ошибка `provider.ErrArtifactsUnavailable`, оборачивается тем же приёмом (`fmt.Errorf("...: %w", ErrArtifactsUnavailable)`), текст называет ОБЕ возможные причины («истёк срок хранения либо джоба не публиковала артефактов»), НЕ хард-фейл — восстановление продолжается без этого конкретного источника (событие `ArtifactsUnavailable`, раздел 4), тем же принципом v0.2.0 «всегда доводить до шелла» (`PROJECT.md`, Key Decisions: «отказ при неопределённости честен, но бесполезен — шелл сам инструмент проверки»).

**Отвергнутая альтернатива:** прерывать воспроизведение отказом, если хотя бы один источник артефактов недоступен — противоречит уже принятому и подтверждённому в v0.2.0 принципу и оставило бы пользователя без шелла из-за истёкшего архива недельной давности, который может быть вообще не нужен для конкретной отладки.

## 6. Встраивание в воспроизведение

**Решение:** (точная точка вызова) `internal/artifacts.Restore` вызывается СРАЗУ ПОСЛЕ успешного `repo.Materialize` (когда `Checkout.Dir` уже существует на диске и его можно наполнять) и ДО `runner.MaterializeFileVars`/`d.EnsureImage` — в ОБОИХ местах, где сегодня вызывается `repo.Materialize`:

- `cmd/ci/main.go`, функция `reproduce`, между строками 338 (конец блока `repo.Materialize`+обработка `code.Persist`) и 361 (`workDir := e.WorkDir()`);
- `internal/ui/session.go`, `PrepareCmd`, между строками 279 (конец блока `repo.Materialize`) и 281 (`workDir := e.WorkDir()`).

Обоснование:

1. артефакты — такая же сетевая операция непредсказуемого размера, как получение кода, и логично встают РЯДОМ с ним, а не перед тяжёлой (часто самой долгой) операцией — тягой образа (`d.EnsureImage`);
2. это продолжает уже принятый в проекте порядок «дешёвое и быстро отказывающее — раньше дорогого» (`cmd/ci/main.go`, комментарий строк 313-316 про `Preflight` перед `Materialize`) — если артефакты превысили предел размера (раздел 4) или недоступны без права доступа (раздел 1), пользователь узнаёт об этом до траты времени на pull образа;
3. `workDir` (значение `CI_PROJECT_DIR`) вычисляется из `env.Environment`, а НЕ из `Checkout`/`artifacts` — значит, распаковка артефактов не должна ждать вычисления `workDir`, она пишет прямо в `Checkout.Dir` (раздел 3), поэтому порядок относительно строки `workDir := e.WorkDir()` неважен, важен только порядок относительно `repo.Materialize` (нужен `Checkout.Dir`) и относительно `RunSteps` (артефакты обязаны быть на месте ДО `before_script`, реальный GitLab-ранер восстанавливает артефакты именно до `before_script`).

**Решение:** (уборка) `internal/artifacts.Restore` не заводит СВОЙ `defer`-уборки — распакованные файлы живут внутри `Checkout.Dir` и убираются вместе с ним существующим `defer code.Remove(...)` (`cmd/ci/main.go:352-356`; аналогично в `internal/ui/session.go`) — вторая точка уборки ради файлов, которые физически лежат в каталоге, уже управляемом первой, не добавляется.

**Отвергнутая альтернатива:** собственный `Result.Remove()` у пакета `internal/artifacts` — раздвоило бы ответственность за один и тот же каталог на диске между двумя независимыми уборщиками, тот же класс дефекта, которым в `internal/repo/checkout.go` (комментарий `Remove`, строки 219-232) уже обоснован ЕДИНСТВЕННЫЙ путь уборки чекаута.

**Решение:** (ошибка внутри Restore) ошибка, кроме «источник недоступен» (раздел 5 — та не прерывает) — например, превышен предел размера (раздел 4) или архив не прошёл проверки безопасности (раздел 8) — прерывает `reproduce`/`PrepareCmd` тем же способом, каким сегодня прерывает ошибка `repo.Materialize`: `return err`/`return fail(err)`, уже зарегистрированный `defer code.Remove` снимет чекаут.

НЕ пытаться воспроизвести джобу БЕЗ артефактов молча, если распаковка провалилась технической ошибкой (не «истёк срок» — это раздел 5, штатная ветка): испорченное/наполовину распакованное состояние рабочего каталога хуже честного отказа, потому что дальше `before_script`/`script` джобы выполнились бы над НЕПОЛНЫМ деревом файлов, и результат «починил, `R`, позеленело» был бы ложным.

## 7. Границы

- **`NEXT-09`** (dotenv-переменные из предыдущих стадий) — ДРУГАЯ форма данных: переменные окружения, которые GitLab передаёт следующей стадии через `artifacts.reports.dotenv` — механически это тоже часть архива артефактов джобы, но потребитель другой (переменные окружения контейнера, не файлы рабочего каталога) и разбор другой (`.env`-формат внутри архива, не произвольные файлы). Эта фаза проектирует только файловую часть (распаковку в рабочий каталог); `dotenv`-отчёты — отдельное требование `NEXT-09`, не смешивается сюда, даже если фаза реализации технически будет читать тот же самый zip — граница по ПОТРЕБИТЕЛЮ данных, не по источнику.
- **`NEXT-04`** (`services`) — не входит: сервисы (например, `postgres:`, `redis:`) — отдельные контейнеры со своим жизненным циклом, никак не связаны с содержимым архива артефактов.
- **`NEXT-06`** (distributed cache из S3) — не входит: кэш (`cache:` ключ джобы) — семантически ДРУГОЙ механизм GitLab (переиспользуемое состояние МЕЖДУ прогонами одной и той же джобы, обычно `node_modules`/зависимости), артефакты — состояние МЕЖДУ джобами одного пайплайна; `ideas/idea-0.2.0` (строки 277-280) уже отвергла смежную идею локальных серверов кэша/артефактов как отдельную крупную работу — то же разграничение подтверждается здесь.
- **`NEXT-02`** (смёрженный конфиг через CI Lint, `include`/`extends`/`!reference`) — джоба с `extends` в конфиге сегодня попадает в `Config.Unresolved` (`internal/provider/gitlab/config.go`, строки 110-118) и её `BeforeScript`/`Script`/`Image` не разбираются вовсе; `Dependencies`/`Needs` такой джобы ТОЖЕ не разбираются — тем же точечным отказом, что применяется к остальным полям `JobConfig` этой джобы, без специального случая для артефактов.
- Не входит (без отдельного `NEXT-*`, но явная граница по объёму фазы): межпроектные/межпайплайновые `needs:` и `parallel:`/матричные джобы — уже названо в разделе 2, здесь только перечисляется как явная граница.
- Не входит: восстановление артефактов для ЧИСТОГО прогона (`runner.CleanRun`/`:clean`) отдельно от первого — артефакты восстанавливаются ОДИН раз, в тот же `Checkout.Dir`, который переиспользуется чистым прогоном (тот же смонтированный каталог, `spec` строится один раз и переиспользуется — комментарий `cmd/ci/main.go`, строки 400-403), повторное скачивание для `:clean` не требуется и не добавляется.

## 8. Безопасность

Архив — недоверенный чужой файл (загружается по ссылке на чужую джобу — тот же trust boundary, что и весь остальной проект).

**Zip slip** (запись за пределы каталога назначения путями вида `../../etc/passwd` внутри записи архива). **Решение:** для КАЖДОЙ записи `*zip.File` перед созданием — собрать целевой путь (`filepath.Join(destDir, f.Name)`), проверить через `filepath.Clean` и сравнение префикса (`strings.HasPrefix(cleaned, destDir+string(os.PathSeparator))` либо эквивалент через `filepath.Rel` без ведущего `..`), что итоговый путь остаётся ВНУТРИ `destDir` (`Checkout.Dir`) — запись, не прошедшая проверку, пропускается с предупреждением (`ArtifactsUnavailable`-подобное событие с причиной «запись архива указывает за пределы рабочего каталога»), архив не отклоняется целиком (одна вредоносная/битая запись не должна лишать артефактов остальные легитимные файлы того же архива).

**Символические ссылки** внутри архива. **Решение:** запись архива с битом режима, кодирующим symlink (`fh.Mode()&os.ModeSymlink != 0` — `archive/zip.FileHeader.Mode()` восстанавливает Unix-биты из `ExternalAttrs`, если архив собран на Unix), НЕ создаётся как символическая ссылка никогда — пропускается с предупреждением, тем же путём, что и zip slip выше. Обоснование: символическая ссылка внутри архива, указывающая наружу `destDir`, а следом обычный файл архива с тем же именем (уже указывающим через ссылку наружу) — классический обход защиты от zip slip через два прохода одного архива; отказ от ЛЮБЫХ символических ссылок из чужого архива закрывает класс целиком, не только простой случай.

**Decompression bomb** (архив с маленьким сжатым размером и огромным распакованным — исчерпание диска). **Решение:** предел раздела 4 (`DefaultArtifactSizeLimit`) применяется к СЖАТОМУ размеру при скачивании (уже решено), И отдельно — предел суммарного РАСПАКОВАННОГО размера при записи (например, тот же порядок величины, 500 МиБ — 2 ГиБ с запасом на типичное соотношение сжатия для текстовых/бинарных артефактов), считается нарастающим итогом по мере записи каждой записи архива через `io.CopyN`/ограниченный `io.Writer`, а не из поля `UncompressedSize64` в заголовке записи (это поле — из заголовка АРХИВА, ему в общем случае доверять для решения «сколько писать» нельзя, оно может быть подделано отдельно от самих сжатых данных).

**Права доступа файлов**. **Решение:** НЕ доверять биту режима из архива буквально; извлечённые файлы получают `fh.Mode().Perm() &^ 0022` (сохраняется бит исполняемости, если он был — артефактам НУЖНО его сохранять: бинарники, собранные более ранней стадией, обязаны остаться исполняемыми в следующей, — но снимается групповая/прочая запись, даже если архив её просил), каталоги — фиксированные `0755`; никакие setuid/setgid/sticky биты не переносятся (Go `archive/zip` их и не восстанавливает через `Mode()`, но явное решение фиксируется на случай будущей реализации через сырые `ExternalAttrs`).

**Библиотека распаковки**. **Решение:** стандартная `archive/zip` (Go stdlib) — стороннюю библиотеку распаковки не вводить. `go.mod` сегодня подтверждает минимальный набор зависимостей (комментарий файла: «один бинарь без зависимостей», `require` — только `yaml.v3`, `charm.land/*`), а `archive/zip` уже покрывает нужный функционал (перечисление записей, потоковое чтение каждой без полной распаковки в память).

**Отвергнутая альтернатива:** сторонний пакет с готовой защитой от zip slip (например, известные обёртки над `archive/zip`) — добавлял бы новую запись в `go.mod` ради логики в пару десятков строк, которую можно и нужно написать самостоятельно и предъявить кодовому ревью проекта (тот же довод, каким в `go.mod` уже обоснован отказ от сторонних пакетов в других частях проекта).

## 9. Интерфейс

**Решение:** артефакты восстанавливаются ФОНОВО, без нового выделенного экрана/колонки — прогресс идёт той же строкой общей ленты подготовки, что и остальные этапы («готовлю код…», «тяну образ…»), опираясь на события раздела 4 (`ArtifactsFetching`/`ArtifactsReady`/…), тем же подписчиком, что уже печатает/отрисовывает `CodePreparing`/`ImagePulling` (`internal/render`, `internal/ui`). Дословно авторская версия уже предполагала это: `idea`, строка 9, баннер подготовки «тяну образ… восстанавливаю артефакты… проставляю окружение…» — фоновая строка, не отдельный интерактивный экран.

**Решение:** (отдельный список/колонка) НЕ проектируется в этой фазе (YAGNI до появления реального использования и обратной связи), но НЕ закрывается архитектурно — `provider.Artifact{Filename, Size, FileType}` (уже существующий тип, `internal/provider/provider.go:120-125`) достаточен как модель данных для будущего списка, если он понадобится; решение фиксирует ТОЛЬКО то, что для v1 реализации `NEXT-03` такой экран не нужен.

**Отвергнутая альтернатива:** сразу проектировать колонку в ленте (по аналогии с колонками окружения/секретов экрана джобы, `JOB-01`) — раздуло бы `ART-01` за пределы вопроса «как тянуть», добавив вопрос «как показывать», который сама формулировка `ART-01` («документ решения») не ставит, и который лучше решать по факту первого использования, а не заранее.

## Открытые вопросы для фазы реализации

- Точная формулировка семантики `dependencies:`/`needs:` (правило (а)-(г) раздела 2) сверяется с актуальной официальной документацией GitLab CI на момент реализации — она зафиксирована здесь по памяти проекта и логике, а не как цитата.
- Конкретное значение `DefaultArtifactSizeLimit` (предложено 500 МиБ) и предел распакованного размера (предложено 500 МиБ — 2 ГиБ) — окончательные числа фаза реализации может скорректировать по опыту первого использования; структура решения (два независимых предела, ни один не полагается на данные из заголовка архива) не должна меняться.
- Точное имя и сигнатура новых полей `provider.JobConfig` (`Dependencies`, `Needs`, `NeedRef`) — зафиксированы здесь как рабочее предложение; финальное имя утверждается кодовым ревью фазы реализации.
- Название и форма события `ArtifactsUnavailable` для случая «запись архива не прошла проверку безопасности» (раздел 8) — сейчас документ описывает его как «`ArtifactsUnavailable`-подобное событие»; фаза реализации решает, отдельный ли это тип события (`ArtifactEntryRejected`?) или переиспользование существующего с другим `Reason`.
